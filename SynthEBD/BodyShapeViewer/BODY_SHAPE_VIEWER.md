# Body-shape viewer (SynthEBD)

SynthEBD's body-shape tooling around the shared character viewer (`SkyRender.Character`'s `VM_CharacterViewer`): BodySlide morphs, key-vertex / bounding-box / region-vertex picking and the pending-box workflow, the zeroed-shape accessors, headless batch deformation, and the measurement / region / slider-heatmap overlays. It lives in the app, not the renderer, and reaches the viewer only through the renderer's neutral seams (the general pipeline is documented in [RENDERING_PIPELINE.md](https://github.com/Synthesis-Collective/SkyRender/blob/main/docs/RENDERING_PIPELINE.md)).

## Shape of the code

| File | What |
|---|---|
| `BodyShapeViewerExtension.cs` | One per viewer. Morph state + `ApplyMorphSet` / `SetMorphContext` / `LoadGuestAsync`, sibling `.tri` probing, picking modes and events, the pending box, pick rows, overlay setters, `GetZeroedShapePositions`, `CreateHeadlessBodyDeformer`, `HighlightSliderMorph`. `viewer.BodyShape()` (or `BodyShapeViewerExtension.For`) finds it. |
| `BodyShapeOverlay.cs` | The overlay channels, an `IRenderOverlay` drawn through the renderer's primitives. |
| `BodySlideDeformer.cs`, `BodyTriFileParser.cs`, `BsdFileParser.cs` (`OsdFile`), `MorphSet.cs` | BodySlide slider deltas from a `.tri` or OSD/BSD data. |
| `HeadlessBodyDeformer.cs` | Viewer-free batch deformation for measurement scans. |
| `SliderHeatmapBuilder.cs` | The slider heatmap geometry. |
| `ClassifierEnums.cs`, `BoxCriterionSelectionTree.cs`, `ShortLabelAttribute.cs` | Box-criterion vocabulary for the picking UI. |

**Attachment.** MainModule registers `VM_CharacterViewer` with an `OnActivated` that attaches the extension to every viewer SynthEBD creates, and configures `BodyShapeViewerExtension.For` for viewers built elsewhere (the offscreen renderer's per-request viewers, reached from `OffscreenRenderRequest.BeforeDraw`). Attaching registers `Overlay` in the viewer's `Renderer.Overlays` and stores the extension in `VM_CharacterViewer.HostData`, which is how `UC_CharacterViewer.xaml` binds the classifier toolbar, pick panel and pending-box editor (`{Binding HostData.X}`).

**Seams used.** Morphs: `ApplyShapeDeformer` with an `IShapeDeformer` whose `Prepare` does the per-application bookkeeping (the zeroed-flip restore point, the sibling `.tri` load) and whose `Deform` applies the slider deltas per shape. Base meshes: `BodyBaseMeshes`. Positions: `TryGetCurrentVertex`, `GetShapePositions`, `GetShapeIndices`, `GetShapeBoneInfo`, `GetCurrentShapeVertexCounts`. Lifetime: `ShapesDeformed` (marker refresh, then `BodySlideApplied`), `SceneCleared` (drop the OSD context, the parsed `.tri`, the missing-`.tri` banner), `GlContextReset`. `CurrentBodyNifDiskPath` locates the `.tri`; `SceneBodyReplacement` decides whether a missing one warns. The extension re-raises `ClassifierControlsAvailable` when the viewer's `RenderingUnavailable` changes.

**Morph application order.** `ApplyMorphSet` (kill switch, then retain the real morph as the viewer's scene input) hands a `MorphSetShapeDeformer` to `ApplyShapeDeformer`, which queues it while the scene isn't ready and drains it at scene commit exactly where the morph used to drain (after texture overrides, before mesh overrides). In `Prepare` the morph becomes the zeroed-flip restore point (unless it *is* the flip), `.tri` is probed next to the body NIF, and the deformation is declined when there is neither a `.tri` nor OSD context. `Deform` prefers the `.tri` (topology-matched) over OSD files. The guest overlay gets a `GuestMorphShapeDeformer` with its own OSD context and its own `.tri`, probed against the guest's body NIF.

## Morphs

### Reading a morph back: `CurrentSceneMorph`

`ApplyMorphSet` only *queues* a morph while the scene is loading or rebuilding (the viewer's `ApplyShapeDeformer` queue, drained when the scene commits), and SynthEBD's host queues one step earlier while the scene isn't ready. A caller that applies a preset and then reads `CpuPositions` (a measurement scan, the BodySlide classifier) must wait until the meshes actually carry it. `CurrentSceneMorph` is the (label, weight) the current scene's meshes are deformed with: set right after the deform loop writes the new positions (not when a morph is queued, and not when there is no delta source, since the meshes are then untouched), cleared when a new scene commits (fresh meshes are at their base). `HasPendingMorphSet` reports a queued morph. Both read the viewer's generic state (`CurrentSceneShapeDeform`, `HasPendingShapeDeformer`) and recognise SynthEBD's own deformer. SynthEBD's `IsBodySlideApplied` / `WaitForBodySlideAppliedAsync` combine these with the host queue. Before this, scans yielded once and measured; a preset still queued at that moment was stored with the previous mesh's values.

### Headless deformation (batch measurement)

[HeadlessBodyDeformer](HeadlessBodyDeformer.cs), built by `BodyShapeViewerExtension.CreateHeadlessBodyDeformer(shapeNames)`, produces the same post-skinning positions `ApplyMorphSet` writes to `GlMesh.CpuPositions`, without the viewer: no normals, no interleaved buffer, no GPU upload, no `BodySlideApplied`. SynthEBD's Match Presets scan uses it to measure presets in parallel.

The viewer's per-shape path (`DeformShape` with this extension's deformer) is `skin(lerp(base0, base1, t) + Σ_k c_k · D_k)`, with `D_k` slider k's morph offset (NIF Z-up deltas converted to Y-up) and `c_k = Big_k/100 · t + Small_k/100 · (1 - t)`. Linear blend skinning is affine per vertex (`CachedSkinTransform.Apply` = rotation · scale · p + translation, blended by normalised bone weights), and the weight lerp is an affine combination, so this equals `lerp(skin(base0), skin(base1), t) + Σ_k c_k · skinOffset(D_k)`. The deformer skins both bases once and builds each slider's sparse table of skinned offsets once (`NifMeshBuilder.SkinOffset`, public in the renderer, which applies `CachedSkinTransform.ApplyLinear` -- rotation **and scale**, no translation; `ApplyRotation`, used for normals, drops the scale and would be wrong here). A preset is then one pass over the base plus a sparse sum. It is exact for any skeleton pose; results differ from the viewer only by float rounding.

*Shape matching in `BodySlideDeformer.BuildSliderDeltaMap` (live, guest and headless paths alike).* An `OsdFile` whose `ShapeName` equals the mesh shape exactly wins: when any file matches exactly, only exact matches apply. Otherwise the long-standing case-insensitive substring rule applies (file-stem names such as `CBBE 3BA Ref` against shape `3BA`). Without the exact rule a multi-shape body crosses data between shapes -- `3BA` is a substring of `3BA_Vagina`, BHUNP's `BaseShape` of `BaseShapeAnus` -- pushing the torso's vertex indices into the smaller shape. The longest-common-prefix stripping that turns `3BA RefAreolaSize` into `AreolaSize` is skipped for `SliderNamesAreCanonical` files, where it would eat a genuinely shared leading word (`VaginaSize`, `VaginaHole` -> `Size`, `Hole`).

Delta-source rules mirror `ApplyMorphSet`: the sibling .tri, when present, supplies every slider (no per-slider OSD fallback); otherwise OSD sources are registered per key (`PrepareOsdSource`; SynthEBD keys them by slider group). The same slider-map builders are shared (`BodySlideDeformer.BuildSliderDeltaMapFromTri` / `BuildSliderDeltaMap`), and an applied slider that references a vertex past the shape's count leaves the shape at its base, as the viewer does. `HeadlessBodyDeformerTests` checks the deformer against the viewer's lerp → `ApplyDeformationFromTri` → `ApplySkinning` sequence on a mesh with scaled, translated bones and partial or zero weights.

### Replacement bodies (source meshes)

The intended input is a BodySlide **source mesh** -- the `ShapeData\<DataFolder>\<SourceFile>` a slider set (`.osp`) builds the worn body from -- which lets a host preview a body type that is not the installed one. Not the `.nif` beside a body's slider-catalog reference `.osd`: those can be a different topology entirely (CBBE 3BA's `CBBE 3BA Ref.nif` is a single 33945-vertex `3BA Ref` shape, while the body BodySlide builds, `SE 3BBB Body Amazing v2.nif`, is `3BA` 18436 + `3BA_Vagina` 1905 + `3BA_Anus` 201, identical to the shipped `femalebody_1.nif`). A source mesh has no `_0`/`_1` pair (the weight morph is skipped) and no sibling `.tri`, so slider deltas take the OSD path; the host must supply the slider set's own slider data (SynthEBD: `SetBodyMorphOsdOverride`), regrouped per target shape. Two facts force the regrouping: a parsed `.osd`'s `ShapeName` is its **file stem** (`SE 3BBB Body Amazing v2`, which matches no mesh shape `3BA`), and a UUNP-style `.bsd` holds one slider and is named after it (`Breasts`). The slider set says what each entry is -- `<Slider name="BigButt"><Data name="3BA_AnusBigButt" target="3BA_Anus">Body v2.osd\3BA_AnusBigButt</Data>` (older sets: `<datafile target="UUNP">Breasts.bsd</datafile>`) -- so SynthEBD's `SynthEbdOsdLoader.LoadFiles` builds one `OsdFile` per target shape (`ShapeName = "3BA_Anus"`), its sliders under their preset names (`BigButt`) and flagged `SliderNamesAreCanonical`. The host must also turn preset values into the values a BodySlide build would use, since a built body has them baked in and a source mesh does not: the slider set's default for every slider the preset doesn't list -- including **hidden** sliders such as 3BA's `NeckSeam` or BHUNP's `Neck` (`small="100" big="0"`), which narrow the neck at weight 0 to meet the vanilla head's weight-0 neck -- then `1 - value` for `invert="true"` sliders, with zap / UV / clamp sliders left out (SynthEBD: `BodySlideBuildRules`, per BodySlideApp's build loop). Skipping this leaves a neck gap below weight 100: measured on CBBE 3BA, the source mesh as-is is up to 0.72 units (0.59 at the neck) from the shipped `femalebody_0`, and exactly equal to it with the rules applied. A missing `.tri` therefore does **not** raise `BodyShapeViewerExtension.BodyTriMissing` for a replaced body (it checks the viewer's `SceneBodyReplacement`) -- the banner is only for the NPC's own worn body.

## Geometry accessors

The renderer's accessors are listed in [RENDERING_PIPELINE.md](https://github.com/Synthesis-Collective/SkyRender/blob/main/docs/RENDERING_PIPELINE.md#geometry-accessors). The extension adds `GetZeroedShapePositions(shape, weight)`: the **sliders-0 (undeformed)** body at the given weight, used to resolve a region's box against the topology-stable reference (see [REGION_VOLUME.md](../REGION_VOLUME.md)).

`GetZeroedShapePositions` re-runs the same base-pose lerp + skinning pipeline as the viewer's deform path but applies **no slider deltas** and is **non-destructive** — it does not touch `CpuPositions`, re-upload to the GPU, or fire `BodySlideApplied` / `ShapesDeformed`, so it's safe to call mid-authoring without flicker or re-entrancy.

## Overlay channels

Each channel is a public collection on `BodyShapeOverlay` — an `IRenderOverlay` the extension registers in the viewer's `GlRenderer.Overlays` when it attaches — cleared+repopulated by a `BodyShapeViewerExtension` setter and drawn through the renderer's generic overlay primitives (`BeginOverlaySurfacePass` / `BeginOverlayLinePass` and the `DrawOverlay*` methods). Host overlays run after the clip-plane visual and before the light gizmos. Drawn in this order (later = on top):

| Channel | Type | Color | Drawn by | Pushed by |
|---|---|---|---|---|
| `KeyVertexMarkers` (+ `BoxResolved`, `PreviewKeyVertex`, `PreviewPick`) | `List<Vector3>` spheres | orange / yellow / green / purple | `DrawOverlayMarkers` (marker pass) | `SetBoxResolvedMarkers`, `SetPreviewPickMarkers`, … |
| `RegionSolidTriangles` | `List<float>` interleaved pos+normal | magenta (`RegionSolidColor`) | `DrawOverlaySolidTriangles` (marker pass, lit) | `SetRegionSolid` |
| `MeasurementRegionTriangles` | `List<float>` interleaved pos+normal | cyan (`MeasurementRegionColor`), or per range (`MeasurementRegionColorRanges`), at `MeasurementRegionAlpha` | `DrawOverlayTranslucentTint` (marker pass, lit, **translucent + depth-tested**, drawn first) | `SetMeasurementRegionTint` |
| `MeasurementLines` | `List<OverlayLineSegment>` | per-segment | `DrawOverlayLines` @ 4.5px | `SetMeasurementLines` |
| `RegionOverlayLines` | same | cyan | `DrawOverlayLines` @ 4.5px | `SetRegionOverlay` |
| `RegionWireLines` | same | cyan | `DrawOverlayLines` @ `RegionWireWidth` (1.25px) | `SetRegionSolid` (wire arg) |
| `RegionCapMarkers` | `List<Vector3>` spheres | cyan | `DrawOverlayMarkers` | `SetRegionOverlay` (verts arg) |
| `SliderHeatmapTriangles` | `List<float>` interleaved pos+normal+**color** | per-vertex ramp | `DrawOverlayVertexColorTriangles` (marker pass, **unlit**, own VAO/shader) | `HighlightSliderMorph` |

Marker spheres are a pre-built 2×-subdivided octahedron (128 tris) scaled by `KeyVertexMarkerRadius × ModelScale` and re-centered per marker. Because each sphere re-uploads ~3 KB, dotting a marker at *every* vertex of a dense cut loop produces an overlapping "beaded cord" and tanks the framerate — which is why the region overlay draws **edges as thin lines**, not a marker per vertex.

**Measurement-region tint (translucent, depth-tested).** `MeasurementRegionTriangles` holds the surface patches of the regions the displayed measurements use (a RegionVolume's region, or the region behind a Region-strategy key vertex). It is drawn first in the marker pass by the renderer's `DrawOverlayTranslucentTint` primitive (mechanics in [RENDERING_PIPELINE.md](https://github.com/Synthesis-Collective/SkyRender/blob/main/docs/RENDERING_PIPELINE.md#the-debug-shader--overlay-gl-state)), lit like the region solid but alpha-blended at `MeasurementRegionAlpha` (0.45, depth writes off) with `glBlendFuncSeparate(SRC_ALPHA, ONE_MINUS_SRC_ALPHA, ZERO, ONE)` — the separate alpha factors keep the destination alpha at 1, so an offscreen BGRA readback doesn't come out semi-transparent where the tint sits — and with the depth test re-enabled for this one draw plus `glPolygonOffset(-1, -2)` on fill, because the patch lies exactly on the body surface and would otherwise z-fight. The result is a surface tint: shaded where the patch is visible, hidden on the far side. This works because the overlay pass draws into the scene FBO whose depth buffer still holds the body (the same reason the wireframe overlay can depth-test). It restores depth-off / opaque / depth-writes-on before the region solid and marker spheres draw. It is a separate channel from the region editor's `RegionSolidTriangles` on purpose: the editor clears and rewrites its channel on every preset change and on region deselect, which would wipe a shared tint. The tint is one color (`MeasurementRegionColor`) unless `MeasurementRegionColorRanges` lists vertex ranges, in which case each range is drawn as its own `glDrawArrays` call with its own `u_color` from the same uploaded buffer (only the listed ranges are drawn). SynthEBD uses this to show a measurement ratio's operands apart: the numerator's regions yellow, the denominator's cyan.

## Overlays in offscreen renders (`BeforeDraw`)

The offscreen renderer draws through the same `GlRenderer.Render`, so every overlay channel above renders into an offscreen image too — if something fills it. Because an overlay is usually computed *from the deformed geometry* (a measurement line joins two resolved key vertices of this preset at this weight), a host can't precompute it before the request: the offscreen scene doesn't exist yet. `OffscreenRenderRequest.BeforeDraw` (an `Action<VM_CharacterViewer>?`) closes that gap. It runs on the render thread against the per-request VM **after** mesh load and texture/mesh overrides and **before** `ConfigureCamera` + `Render`. SynthEBD's hooks first apply the preset (`vm.BodyShape().ApplyMorphSet`, which attaches the extension to the per-request viewer and deforms immediately -- the request no longer has a morph field), then push the overlay (e.g. `SetMeasurementLines`) from this render's deformed positions, drawn in the same frame.

The per-request VM is created fresh for every render (by `NpcSceneBuilder`, the NPC `IOffscreenSceneBuilder`; the offscreen renderer itself only owns the context, framebuffers, asset scopes and readback), so a hook's overlay can't leak into a later request (including the software fallback preview, which shares the renderer). The hook must not touch WPF objects — it isn't on the dispatcher thread — and a throwing hook is logged and costs only the overlay; the frame still renders. SynthEBD's Show Spread window uses it to draw a metric's measurement lines on each thumbnail, and to tint any region the measurement uses (a RegionVolume's region, or the region behind a Region-strategy key vertex) translucent cyan through the measurement-region tint channel (`SetMeasurementRegionTint`), the same one the live viewer's measurement overlay uses. Null `BeforeDraw` leaves the offscreen path byte-identical to before.

## Region overlay (BodySlide classifier)

A RegionVolume region's selected-state visualization has two modes (editor `RegionViewMode`), both built from the baked `ResolvedRegion` evaluated against the current deformed positions (so they track the previewed preset):

- **End-Cap** (default): the cyan cut-loop contour only, pushed to `RegionOverlayLines` (thick) — a clean curve, no per-vertex markers.
- **Solid**: the magenta region surface (patch + caps) as a lit solid in `RegionSolidTriangles`, plus a thin cyan triangle-edge **wireframe** in `RegionWireLines`. Faces = solid, vertices/edges = wireframe.

The geometry is generated by `RegionVolumeEvaluator.BuildSolidSurface` (interleaved pos+normal triangles, flat per-tri normals) and `BuildSolidWireframe` (deduped patch edges). The pending-box wireframe (the AABB you draw/edit) is a separate WPF `Canvas` overlay in [UC_CharacterViewer.xaml.cs](../Classes_Aux/Views/UC_CharacterViewer.xaml.cs) `UpdateBoxWireframe`, not part of this GL pass. The measurement algorithm behind all of this — zeroed-space authoring, cross-preset tracking, cap modes, rotation — is documented separately in [REGION_VOLUME.md](../REGION_VOLUME.md).

## Slider-morph heatmap (Label by Sliders annotator)

The OBody **Label by Sliders** rule editor can highlight, on its embedded preview, exactly which body vertices a designated BodySlide slider moves — so a rule author can see what `BellyMuscle` or `Waist` actually controls before writing a threshold against it. It is the one overlay that scales to **thousands** of vertices, so it deliberately reuses the *batched* upload model (one `BufferData` + one `DrawArrays`, like `DrawOverlaySolidTriangles`) rather than the per-element marker/line paths, which the note above warns tank the framerate at high counts.

- **Data.** A slider's per-vertex morph deltas are already a sparse `Dictionary<ushort, Vector3>` (vertexIndex → offset) inside the loaded `.tri`/OSD context. `BodySlideDeformer.TryGetSliderDeltas(slider, shape, tri, osd)` returns it, reusing the same `.tri`-over-OSD preference and OSD longest-common-prefix name-stripping as `ApplyMorphSet` — **no file re-parse**. The set is direction-agnostic: `Small`/`Big` scale this one geometric morph, so the moved-vertex set is identical at any weight.
- **Geometry + color.** `SliderHeatmapBuilder.Build` (pure, unit-tested) walks the shape's `CpuIndices` against its current deformed `CpuPositions`, keeps vertices whose `|delta|` exceeds `DefaultMinDelta` (~1e-4 mesh units, dropping near-zero authored noise), and emits every triangle with **any** affected corner as interleaved `pos+normal+color`. Color grades `|delta|` against the slider's own max through a jet-style ramp (`Ramp`, blue→cyan→green→yellow→red); unaffected corners of an emitted triangle take the cold end, giving a soft falloff at the patch boundary. `BodyShapeViewerExtension.HighlightSliderMorph` fans this over every cached body shape into `SliderHeatmapTriangles`; `ClearSliderHighlight` empties the channel.
- **Draw.** `DrawOverlayVertexColorTriangles` runs at the end of the marker pass (depth still off, back-face cull still on) with its own unlit shader/VAO, so the patch reads as an always-on-top magnitude map. It is rebuilt on every preset/weight/NPC change because `VM_SliderAnnotatorPreviewPanel` re-applies it from the viewer's `BodySlideApplied` event (which also covers queued-morph replays), tracking the current pose.

## Region vertex-edit pick mode

Beyond drawing a box, a region's selection can be hand-curated vertex by vertex (the Option-B edit layer in [REGION_VOLUME.md](../REGION_VOLUME.md)). This adds **no new GL channel** — it reuses the existing pick plumbing and the **preview-marker channel**:

- **Mode + direction.** `BodyShapeViewerExtension.IsRegionVertexEditMode` (a third pick mode alongside `IsKeyVertexPickMode` / `IsBoundingBoxPickMode`) and `RegionVertexEditAdditive` (Add vs Remove) are bound to two toolbar checkboxes. While the mode is on, the view's mouse handlers suppress orbit.
- **Pick.** A left-click ray-picks the nearest vertex (`HitTestKeyVertex`); a left-drag rubber-bands the shared `BoxSelectionRect` and bulk-selects every enclosed vertex by re-projecting the mesh (`BuildRegionVertexEditFromScreenRect`, the same projection as `ComputeBoxFromScreenRect`). Either way the affected vertices' **zeroed** positions are looked up (`GetZeroedShapePositions`, so the stored edit is display-space-independent) and fanned out as a `RegionVertexEditPick` through `RegionVertexEdited` / `AnyRegionVertexEdited` to the editor VM.
- **Live selection overlay (recolored wireframe).** Rather than dropping marker spheres, the editor recolors the region's **wireframe** to show the edits. In Solid view mode it pushes per-segment-colored line segments through `SetRegionWireColored` (which fills the `RegionWireLines` channel — already per-segment colored): untouched patch edges stay cyan, the half of each edge nearest a curated **added** vertex is green (a whole edge between two added vertices is fully green), and **removed** vertices — which have no edges, having been carved out of the patch — plus any *isolated* added vertex (no triangle formed yet) get small **node crosses** (red / green, three short axis segments) sized to the local mean edge length. The half-edge tagging comes from `RegionVolumeEvaluator.BuildTaggedWireframe`, which flags each patch-edge endpoint whose welded vertex is a whole-triangle corner at an added mesh index. In End-Cap mode the clean cyan contour is kept and only the node crosses are drawn. The induced patch's contour / Solid surface re-resolve through the normal region-overlay channels on every edit. (The old `PreviewPickMarkers` sphere path is explicitly cleared, so no spheres linger.)
